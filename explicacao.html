0. Conceitos básicos (o mínimo para entender tudo)

Processo, thread, núcleo

  • Núcleo (core): a unidade física da CPU que executa instruções. O nó usado tem 8 núcleos físicos (2× Xeon E5520).
  • Hyper-thread (HT): cada núcleo físico finge ser 2 núcleos lógicos (o nproc mostra 16). As 2 threads dividem as unidades de execução do núcleo: ajuda, mas não dobra o desempenho.
  • Thread (software): linha de execução dentro de um processo. Criamos até 16 threads OpenMP e o sistema as distribui pelos núcleos.

Speed-up e eficiência

  • Speed-up S(p) = Tseq / T(p): quantas vezes o programa paralelo com p threads é mais rápido que o sequencial. Ideal: S(p) = p.
  • Eficiência E(p) = S(p) / p: fração do ideal aproveitada. 100% = perfeito. Sempre cai quando p cresce (barreiras, parte serial, comunicação, desbalanceamento).
  • Lei de Amdahl: a parte do programa que é serial (não paralelizável) limita o ganho máximo, não importa quantas threads você use.

Escalabilidade forte × fraca

  • Forte: tamanho do problema fixo, aumenta as threads. Pergunta: "com mais mão de obra, o mesmo trabalho termina mais rápido?"
  • Fraca: o trabalho cresce junto com as threads (carga por thread constante). Pergunta: "consigo resolver um problema maior no mesmo tempo?" O ideal é o tempo ficar constante (eficiência 100%).

1. O problema: conjunto de Mandelbrot

Para cada pixel c da imagem, repetimos z = z² + c (começando de z = 0) até |z| > 2 (ponto "escapou") ou até max_iter = 2000 iterações. O tom do pixel é proporcional ao número de iterações. Três fatos importam:

  1. Pixels são 100% independentes: calcular um pixel nunca precisa do resultado de outro. É o paralelismo mais fácil que existe ("embaraçosamente paralelo").
  2. O custo por pixel varia até 1000×: pixel fora do conjunto escapa em poucas iterações; pixel dentro do conjunto roda as 2000 iterações inteiras.
  3. O interior do conjunto fica no centro da imagem: logo as linhas centrais são muito mais caras que as das bordas — e ninguém sabe de antemão quais linhas são caras. Esse desbalanceamento intrínseco é o tema central do trabalho.

Paralelizamos o laço das linhas (não pixel a pixel: abrir região paralela para cada pixel seria caro demais; e não o laço interno, que é sequencial por natureza). Cada thread escreve uma faixa disjunta da imagem: sem escrita compartilhada, sem critical, sem atomic no laço.

2. OpenMP básico

OpenMP é um conjunto de diretivas de compilador (#pragma omp ...) para paralelismo com memória compartilhada, em modelo fork-join: o programa começa serial, abre uma equipe de threads na região paralela e volta a ser serial no fim.

gcc -O2 -o mandelbrot_seq mandelbrot.c -lm            # sequencial
gcc -O2 -fopenmp -o mandelbrot_par mandelbrot.c -lm   # paralela

O truque do trabalho: é o mesmo arquivo-fonte. Sem -fopenmp o compilador ignora os pragmas e gera o sequencial; com a flag, gera o paralelo. Mesma otimização -O2 nos dois — assim o T(1) de referência é honesto e o speed-up não sai inflado.

As diretivas que usamos (todas numa linha!)

#pragma omp parallel for schedule(runtime) reduction(+:checksum)
  • parallel for: divide as iterações do laço for seguinte entre as threads.
  • schedule(runtime): quem decide como dividir é a escolha feita em tempo de execução (via omp_set_schedule, controlada pela nossa flag -s/-c). Isso permite comparar escalonadores com o binário idêntico, sem recompilar — comparação justa.
  • static: divide as linhas em blocos contíguos fixos antes de começar (rápido, mas se um bloco tem as linhas caras, aquela thread atrasa todas).
  • dynamic,chunk: threads livres pegam pacotes de chunk linhas de uma fila (balanceia, custa sincronização).
  • guided: começa com pacotes grandes e vai diminuindo.
  • reduction(+:checksum): o checksum (soma das iterações, nossa prova de corretude) é o único acumulador compartilhado. A redução dá uma cópia privada a cada thread e soma tudo no fim — sem ela precisaríamos de atomic, que serializaria o laço quente.
  • Variáveis declaradas dentro do laço (x, cr, ci, it) são automaticamente privadas por thread. É a forma mais segura de evitar compartilhamento acidental.
  • OMP_PLACES=cores + OMP_PROC_BIND=close: prendem cada thread ao seu núcleo (o SO não fica migrando thread de núcleo, o que embaralharia os tempos).

3. O código, parte por parte

mandel_ponto(cr, ci, max_iter) — o núcleo

Executa z = z² + c e devolve em quantas iterações o ponto escapou (compara zr*zr + zi*zi <= 4.0, isto é, |z|² ≤ 4 — evita a raiz quadrada, que é cara). É aqui que nasce o desbalanceamento: retorno pequeno = pixel barato, retorno = max_iter = pixel caro.

main — argumentos e laço

Lê -w -a -i -t -s -c -o (largura, altura, max_iter, threads, scheduler, chunk, imagem de saída). Calcula o passo no plano complexo uma vez, fora do laço. Roda o laço duplo (linhas fora, colunas dentro) com o pragma do item 2, acumulando o checksum. Imprime uma linha CSV: modo;threads;schedule;chunk;largura;altura;max_iter;tempo;checksum. O checksum 7591159335 saiu idêntico em todas as execuções da forte — prova de que o paralelo calcula exatamente o mesmo que o sequencial.

Scripts

  • medir.sh: roda cada configuração 3 vezes e guarda a mediana (não a média — uma execução contaminada distorce a média, mas não a mediana). Gera resultados/forte.csv, fraca.csv e sched.csv.
  • ht.sh: só anexa o ponto de 16 threads aos CSVs já existentes.
  • analisar.sh: calcula speed-up e eficiência e avisa se algum checksum divergir.
  • job.sh / ht.sh: enviados com sbatch --exclusive (nó dedicado — sem outro grupo dividindo a máquina, os tempos valem para speed-up).
  • graficos.py: desenha as figuras a partir dos mesmos CSVs.

4. Metodologia (como medir direito)

  • Máquina: nó atlantica05 — 2× Xeon E5520 2,27 GHz (8 núcleos físicos / 16 threads), 15 GB RAM, gcc 9.4.0, -O2.
  • T(1) do binário sequencial real, 1 núcleo.
  • Forte: imagem fixa 4096×4096, threads 1, 2, 4, 8 (+ 16 HT), 3 escalonadores.
  • Fraca: 1024×1024 pixels por thread, lado escalado por √p sobre a mesma janela (preserva a distribuição do custo).

Hiper-threads (o ponto 16)

O dynamic sobe de S=6,90 (8 threads) para S=12,07 (16 threads), com a eficiência indo de 86,3% a 75,4%: a segunda thread de cada núcleo divide as unidades de execução, então o ganho é sublinear — o limite passa a ser o núcleo, não a distribuição de carga. É o ponto 16 das figuras.

7. Para a apresentação (o que cada um precisa saber)

  • Por que Mandelbrot? pixels independentes + custo por pixel imprevisível → desbalanceamento real para o OpenMP resolver.
  • Por que linhas e não pixels? granularidade: abrir região paralela por pixel custaria mais que o cálculo; por linha, cada thread escreve faixa própria.
  • Por que dynamic ganha? fila sob demanda corrige o desbalanceamento; static prende linhas caras às mesmas threads.
  • O que é o ponto 16? hyper-threads: mais throughput (12,07), menos eficiência (75,4%) — núcleo compartilhado.
  • Como provam que está certo? checksum idêntico + imagens binárias iguais.
